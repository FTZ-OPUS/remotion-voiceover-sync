# 踩坑与修复详解

记录从"PPT 转 Remotion 动画 + 配音对齐"过程中踩过的每一个坑，按严重程度排序。

---

## 坑 1（致命）：用全局变速/拉长"对齐"配音

### 现象
配音是一次性生成的连续音频（56 秒），视频 64.5 秒。为了让时长一致，给 `<Audio>` 加 `playbackRate={0.9}` 或用 ffmpeg `atempo` 拉长。总时长对齐了，但用户反馈："你只是跟视频时长对齐了，但具体的帧根本没对齐，一点都不齐，全程都偏了。"

### 根因
全局变速是**均匀拉伸**，只能让总时长匹配，无法让每句话对应到正确的场景。比如第 3 句话讲"位置"，变速后它可能落在"定义"场景。而且 `playbackRate` 改变的是播放速度，音频内容的时间分布被整体压缩/拉伸，和画面的场景切换点完全无关。

### 解决方案
**彻底放弃全局变速**。改为：
1. 按场景分段生成配音（每段内容严格对应一个场景）
2. 裁掉每段开头静音
3. 用 ffmpeg `adelay` 把每段精确放到对应场景的时间轴位置
4. 拼接成完整音轨

这样每段配音的起始位置是**确定性的**，等于 `场景起始帧 + 固定偏移`，和画面场景严格对应。

## 坑 2（致命）：一次性生成连续配音

### 现象
写一整篇连续配音稿，一次性生成 56 秒音频。然后试图通过变速或调整场景时长来对齐。

### 根因
连续音频中，哪句话在哪个时间点是 TTS 模型决定的，不可控。你无法提前知道"关系代词"这几个字在第几秒，也就无法让画面在那个时间点显示关系代词表格。即使检测了句内时间，也无法把它们映射到场景——因为连续音频的句子边界和场景边界不重合。

### 解决方案
**按场景分段生成**。为每个场景写独立的配音稿，逐段调用 TTS。这样：
- 每段的内容和场景一一对应
- 每段可以独立裁剪、独立定位
- 拼接时每段放在对应场景的位置，天然对齐

代价：需要调用 N 次 TTS（N=场景数），但这是值得的。

---

## 坑 3（关键）：TTS 音频开头静音长度不一

### 现象
按场景分段生成后，用 ffmpeg 把每段 `adelay` 到设计位置。但实际播放时，有的场景配音早了、有的晚了，偏差从 0.3 秒到 1.8 秒不等。

### 根因
TTS 生成的音频，**开头静音长度不固定**。检测发现：
- s01 开头静音 1.75 秒
- s02 开头静音 1.30 秒
- s03 开头静音 0.85 秒
- 其他段 0.3~1.0 秒不等

`adelay` 只是把整段音频（含开头静音）后移，所以实际语音起始 = 设计位置 + 开头静音长度。开头静音越长，配音越晚。

### 解决方案
**裁掉每段开头静音，保留固定 0.15 秒**。

```bash
# 检测开头静音
ffmpeg -i s01.wav -af silencedetect=noise=-35dB:d=0.2 -f null - 2>&1 | grep silence_end
# 裁剪（保留 0.15s）
ffmpeg -i s01.wav -ss <静音结束-0.15> -c copy trimmed/s01.wav
```

裁剪后所有段的开头静音统一为 0.15 秒，实际语音起始 = 设计位置 + 0.15 秒，偏差可预期且一致。

## 坑 4（关键）：playbackRate 后嘴型错位

### 现象
给 `<Audio>` 加了 `playbackRate={0.9}` 后，数字人嘴巴的开合和声音对不上——声音慢了，但嘴型还是按原速动。

### 根因
`useAudioData` 加载的是原始音频文件，`visualizeAudio` 按原始采样率计算每帧音量。但 `<Audio playbackRate={0.9}>` 播放时声音被放慢了，**useAudioData 不知道 playbackRate**，它仍然按原速返回音量数据。结果：嘴型按原速动，声音按 0.9 倍速播，越往后错位越大。

### 解决方案
**不要用 playbackRate**。改用分段对齐（见坑 1），让音轨本身就和视频等长，Audio 正常播放即可。此时 useAudioData 和 Audio 加载同一文件、同一速度，嘴型自然同步。

---

## 坑 5（中等）：Audio 和 useAudioData 加载不同文件

### 现象
数字人嘴型偶尔错位，或在某些场景嘴巴不动。

### 根因
早期版本中，`<Audio>` 播放的是一个文件，`useAudioData` 加载的是另一个文件（比如一个是分段拼接版、一个是原始连续版）。两个文件的时间轴不同，嘴型当然对不上。

### 解决方案
**Audio 和 useAudioData 必须加载同一个文件**：

```tsx
<Audio src={staticFile("voiceover_track.wav")} />
const audioData = useAudioData(staticFile("voiceover_track.wav"));
```

且都不加 playbackRate。

## 坑 6（中等）：TransitionSeries 总时长算错

### 现象
11 个场景，每个 `durationInFrames` 设为 D[i]，以为总时长 = sum(D)。实际渲染出来总时长比 sum(D) 短。

### 根因
`TransitionSeries` 的转场是**重叠交叉**的。每个转场持续 TRANSITION 帧，这期间前一个场景淡出、后一个场景淡入，两者重叠。所以：

```
总时长 = sum(SCENE_DURATIONS) - (场景数 - 1) × TRANSITION
```

11 个场景、10 个转场、每个 15 帧，总时长比 sum(D) 少 150 帧（5 秒）。

### 解决方案
计算场景全局起始帧时必须减去转场：

```ts
const starts = [0];
for (let i = 1; i < D.length; i++) {
  starts[i] = starts[i-1] + D[i-1] - TRANSITION;
}
const total = starts[starts.length-1] + D[D.length-1];
```

配音拼接时用这个 `starts` 作为每段的全局起始位置。

## 坑 7（中等）：Remotion translate 插值单位

### 现象
`translate: interpolate(frame, [0, 30], ["0 30px", "0 0px"])` 报错或不生效。

### 根因
Remotion 的 translate 插值要求**每个值的单位完整**。`"0 30px"` 中第一个值 `0` 没有单位，应该是 `"0px 30px"`。

### 解决方案
```tsx
translate: interpolate(frame, [0, 30], ["0px 30px", "0px 0px"], {...})
```

## 坑 8（中等）：互相关验证用开头模板匹配失败

### 现象
用每段配音的前 2 秒做模板，在成片中做归一化互相关定位。某一段（s05）相关系数仅 0.075，定位偏差 77 帧，误以为错位。

### 根因
s05 配音开头是"只能用 that 的情况有三种"，前 2 秒包含弱能量的开头和停顿，模板特征不明显。互相关找到了错误的峰值。

### 解决方案
**用中段模板验证**，或用多个不同位置的模板交叉验证：

```python
# 不要只用 [0:2s]，用 [2:3.5s]、[4:5.5s] 等中段
for (a, b) in [(2.0, 3.5), (4.0, 5.5), (6.0, 7.5)]:
    tpl = seg[int(a*SR):int(b*SR)]
    # 定位后隐含段首 = 定位时间 - a
```

如果多个中段模板一致指向同一个段首位置，就是对齐的。同时配合静音检测交叉验证。

## 坑 9（低）：doubaocdn 音频链接失效

### 现象
`text_to_audio_plus` 返回的 doubaocdn 链接，过几分钟再下载就 404。

### 根因
doubaocdn 的音频链接可能有较短的有效期。

### 解决方案
**生成后立即下载**。不要攒一批再下，逐段生成逐段下。

---

## 坑 10（低）：curl 下载频繁超时

### 现象
`curl -L -o file.wav "https://aka.doubaocdn.com/..."` 频繁 SSL EOF 或超时。

### 解决方案
用 Python urllib 更可靠，加多重试：

```python
import urllib.request, time
for attempt in range(5):
    try:
        urllib.request.urlretrieve(url, path)
        break
    except Exception as e:
        time.sleep(2)
```

## 坑 11（环境）：工具周期性超时

### 现象
所有工具调用（Bash/Read/Edit/Grep）突然全部超时，持续十几分钟无法恢复。

### 根因
执行环境/应用层面的周期性故障，不是任务本身的问题。

### 解决方案
**重启豆包应用**可恢复。重启后任务数据不丢，继续即可。如果频繁出现，检查是否有其他进程占满 CPU/内存（比如未退出的渲染进程）。

---

## 坑 12（工具）：Edit 要求先完整 Read

### 现象
用 `Read` 分段读取文件（`limit=100` + `offset=100`）后，调用 `Edit` 报错 "File has not been read yet"。

### 根因
Edit 工具要求**一次完整的 Read**（不带 limit/offset），分段读取不被识别。

### 解决方案
编辑前用 `Read` 完整读取整个文件（不带 limit/offset），再 Edit。

---

## 总结：对齐质量的三层保障

| 层级 | 方法 | 验证标准 |
|------|------|----------|
| 场景级 | 分段配音 + adelay 精确放置 | 每段在场景开始+0.6s开口 |
| 句子级 | 检测句内时间 + 文字动画按帧对齐 | 每个知识点出现时配音正好讲到 |
| 嘴型级 | Audio/useAudioData 同文件无变速 | 嘴巴开合与声音能量同步 |

三层都做到，才是真正的"逐帧对齐"。任何一层缺失，用户都会感觉到"不同步"。
